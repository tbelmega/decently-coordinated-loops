# The work-stream board

One board tracks all parallel dev work-streams across projects, agent harnesses, and
machines. It lives in the **data repo** your global config block points at (the private
repository containing `BOARD.md`); run every command below from its root.

This skill and the other loops-* skills define the generic contract. Local policy lives in
the data repo: `HOUSE-RULES.md` (cross-project policy; "the owner" is the human named in
`HOUSE-RULES.md → Owner`) and `PROJECTS.md` + `loops.json` (the project registry).
Resolve "per house rules" and "per the project entry" there, never from memory or
hardcoded paths.

## Three artifacts, three writers

| Artifact | Writer | Role |
| --- | --- | --- |
| `items/*.md` | agents (hand-edited) | **source of truth**: all fields, full detail, logs |
| `BOARD.md` | derived | flat machine-readable index, regenerated by `bun run sync` |
| `ARCHIVE.md` + `archive/`, `for-delivery/` | derived | terminal and verified-but-unreleased items, moved by sync |

`BOARD.md` is derived: the item file always wins. You may hand-edit a row between syncs
for immediacy; `bun run check` fails on rows that disagree with the items, and the next
`bun run sync` repairs them.

## States

The single source of truth for `state:` values (`bun run check` rejects anything else):

`idea → spec-filed → in-progress → implemented → merged → tested → delivered → accepted`

| State | Meaning | Folder |
| --- | --- | --- |
| `idea` / `spec-filed` / `in-progress` | pre-integration lifecycle | `items/` |
| `implemented` | change complete on its agent branch; review requested per `HOUSE-RULES.md → Review mechanism` | `items/` |
| `merged` | integrated into the project's integration branch; item becomes agent-owned for verification | `items/` |
| `tested` | agent-verified per the project's verify gate (loops-pickup → "Verify an integrated item") | `for-delivery/`, or `archive/` under a `no-deploy` tail |
| `delivered` | released to the owner's staging/production environment | `for-delivery/` |
| `accepted` | owner tested the release and accepted | `archive/` |
| `blocked` | waiting on a decision / another item / outage | `items/` |
| `dropped` | abandoned | `archive/` |

**Where the tail ends is per project.** `loops.json` may declare
`"lifecycle": "no-deploy"` for a project with no release event (its artifact reaches users
through a clone or a merge, not a deploy). There `tested` is terminal: the item archives
as `tested` with an `ARCHIVE.md` row, `next-actor: agent`, no `awaiting`, and a
`next-step` reading "None - ...", and nothing rewrites it to `accepted`, because the record
must never claim an owner action that did not happen. Every other project, registered or
not, keeps the `deploy` tail (`tested → delivered → accepted`). Sync never moves a file
out of `archive/`, so reopening an archived item is a hand move. When declaring or
changing a project's `lifecycle`, or reopening an archived item, read
`references/lifecycle-tails.md`.

Record integration with `bun run check-integration-status --apply`: it sets `merged`,
`next-actor: agent`, `autonomy: auto`, and `next-step: "Verify per the project verify
gate, then flip to tested"`, so the item is immediately agent-pickable; recording `merged`
by hand writes the same four fields. Who owns an `implemented` item depends on the
instance merge policy: owner-owned integration waits in `review-merge`, explicitly
delegated merges stay agent-owned.

| State | next-actor | awaiting |
| --- | --- | --- |
| `implemented` | owner | `review-merge` |
| `implemented` | agent | - |
| `merged` | agent | - |
| `tested` (`deploy` tail) | owner | `deliver` |
| `tested` (`no-deploy` tail, terminal) | agent | - |
| `delivered` | owner | `accept` |

## Project participation

Your always-on config block defines the participation gate (`cli-registered.ts`, run
from the checkout in question; the data repo itself counts as registered) and the
registration offer. Two facts it leaves out:

- **Worktrees resolve to their main checkout**: a linked worktree of a registered repo is
  registered.
- **Gate exemptions.** `HOUSE-RULES.md` may declare obligations that follow an *action*
  rather than a *directory* (e.g. "after refreshing the design export, file board items
  for newly-buildable work"). Those apply from any checkout; everything else respects the
  gate.

## Item file schema - `items/<project>-<slug>.md`

```markdown
---
title: Short human title
project: <name registered in PROJECTS.md>
state: in-progress
assignee: <durable harness/account-or-slot lane driving the item>, or "-"
autonomy: auto | supervised   # auto = the owner pre-approves unattended pickup
next-actor: owner | agent     # whose move is it? if an agent can't proceed without
  the owner's input, the ball is in the owner's court, even pre-implementation
awaiting: unblock | review-merge | deliver | accept | approve | decide
  # only when next-actor: owner: the action-type bucket
fit: optional one-line capability hint (e.g. "mechanical, spec is exact" or
  "needs frontier: cross-module design judgment"); set when filing, refining,
  or passing on the item (loops-pickup capability gate)
spec: waived   # optional; the owner's explicit call that this item needs no
  spec despite its size; `autonomy: auto` alone never implies this
  (loops-pickup → Spec gate)
depends-on: [item-slug, ...]   # items whose MERGED output this one needs; omit if
  none. Mandatory for descriptive items (below)
tickets: [ABC-123, ABC-130]   # only for a project with a tracker. GitHub ids need
  quotes ("#123"), or YAML reads the hash as a comment. `tickets: local` = stays on
  the board; omitted = undecided
next-step: The single concrete next action. Mandatory; never leave stale.
updated: YYYY-MM-DD
execution:                    # last-recorded location; not liveness or a lock
  host: <opaque host name>
  worktree: <absolute Git worktree path on that host>
links:
  spec: docs/specs/...        # omit keys that don't apply
  spec-branch: <pushed agent branch carrying an approved, not-yet-merged spec>
  spec-sha: <the spec commit on spec-branch>
  branch: <agent branch>
  pr: <review URL, when the review mechanism is PR-based>
  stack-parent: <preceding item in this worktree stack>
  base-sha: <commit at which this item's implementation began>
  head-sha: <reviewed handoff commit for this item>
---

One short paragraph of context: what this is and why.

## Log
- YYYY-MM-DD: dated one-liners, append-only, newest last.
```

`bun run check` names every schema violation it can see (blank required fields, closed
sets, `execution` shape, ticket ids, the `spec-filed` and `spec-branch`/`spec-sha` links,
`assignee` beside a legacy `owner:`); fix the cause it reports.

**Assignee and execution.** `assignee` is assignment, not execution identity: an opaque
harness plus account/slot lane, never a model, host, worktree, or session. Readers accept
a legacy `owner:` key as a fallback, but new and substantively updated items write only
`assignee:`. `execution` records where the work last was; it does not prove the host or
process is alive, and push atomicity stays the claim lock. **Record the machine in
`execution.host`**, never in the assignee string (a lane can move machines); check
requires it once an `in-progress`, `implemented` or `blocked` item names `links.branch`,
and whenever `execution.worktree` is set. If you cannot state the host truthfully, omit
it: its readers fail closed on absence and act on a recorded value, so a guess is worse
than nothing.

## Dependencies & readiness

`depends-on` lists the items whose **integrated** output an item needs to be correct. It
is a durable structural fact set at filing time, not a status; "blocked on a dependency"
is derived from it and the targets' merged status, never stored separately.

A target is **satisfied** only when its work is on the project's integration branch:
`bun run check-integration-status` reports it MERGED, or its state is
`merged`/`tested`/`delivered`/`accepted`. `implemented` is **not** satisfied (review
requested is not merged), nor is `dropped`. Exception: deliberate stacking within one
permanent slot may build on an unmerged target when the new item records that target as
`links.stack-parent`, its `links.base-sha` equals the target's `links.head-sha`, and Git
confirms that commit is the new branch's ancestor. This exact relationship satisfies a
dependency for the stacked item; a shared branch name alone does not. (`bun run ready`
does not know this exception; check it yourself.)

**Descriptive vs prescriptive.** A *descriptive* item, documenting behavior that already
exists (runbooks, references, "how it works" notes), must declare `depends-on` for every
implementation item it describes. A *prescriptive* item, driving what gets built (specs,
plans, ADRs), declares no such dependency.

An item with any unsatisfied dependency is not eligible for pickup (loops-pickup).

## Specs vs. items

The item is lifecycle + coordination; it never *becomes* the spec. The spec lives in the
project repo at its registered specs location (`PROJECTS.md`), referenced via
`links.spec`, where it versions with the code it governs and survives the item's archival.

- **`spec-filed` means** an owner-approved spec is committed in the project repo at
  `links.spec`. Skipping `spec-filed` on the way to `in-progress` is legitimate only for
  items small enough that the item description suffices (loops-pickup → Spec gate) or
  carrying the owner's explicit `spec: waived`. Check enforces only the link's presence;
  approval and reachability stay your judgment.
- **Draft design content lives on the board** (the item's `## Refinement` section) until
  the owner approves it. Agents never commit unapproved design to a project repo
  unattended, not even on agent branches.
- **Owner-facing drafts lead with the asks.** An item awaiting the owner's ruling
  (`awaiting: approve`/`decide`) opens, right after the context paragraph, with a
  `### Decisions needed` block: each open decision on one line with a recommendation.
  Mirror them to the outbox per loops-queues.
- **Approval is the gate; promotion is agent work.** Approval arrives via the outbox
  (`awaiting: approve`) or an attended session. Once given: commit the approved content
  as the spec at the project's specs location, set `links.spec`, annotate the
  `## Refinement` section as promoted (the spec is now the source of truth), flip the
  state to `spec-filed`, and log it.
- **A `spec-filed` spec must be reachable by other agents.** Flip to `spec-filed` only
  when the spec commit is on the project's integration branch, or pushed on an agent
  branch recorded as `links.spec-branch` (+ `links.spec-sha`); a spec only in a local
  checkout is not filed. Implementation bases on that recorded branch/commit (as a stack
  where the project uses permanent slots), so the spec is in the implementor's tree.
  (`links.branch`/`base-sha`/`head-sha` stay reserved for the reviewed implementation
  range; the integration check reads them.)

## Update rules

1. **Read `BOARD.md` before starting a work-stream** in a registered project. Errands
   skip the board.
2. When an item's state or next step changes: update its item file (state, next-step,
   next-actor, awaiting, updated, append a log line), then run `bun run sync` (or
   hand-edit the board row when a sync isn't warranted).
3. New work-stream → new item file. Don't fold unrelated work into an existing item. Set
   `depends-on` at filing (mandatory for descriptive items).
4. Other items belong to other agents/sessions: update them only on real state changes
   you caused or observed; append to their logs, never rewrite them.
5. Just set the state: `bun run sync` moves the file to the folder the States table names
   and appends the `ARCHIVE.md` row.
6. Commit immediately after updating (imperative subject, e.g. `Move feature-x to
   implemented`), and push if the remote is reachable (Concurrency).

## Concurrency

Within one checkout, `bun run sync` takes its own lock (`.loops-sync.lock`) and waits or
aborts on its own; stale locks are broken automatically. Uncommitted edits in a shared
data-repo checkout can be lost to another session's rebase, so commit board edits at once.

Across machines, **origin is the source of truth, and git push atomicity is the
distributed lock**:

- **A claim or state change is only real once pushed.** A rejected push means the world
  moved: `git pull --rebase`, re-read the affected item, re-decide. If your claim
  survived, push again; if someone else's assignee is on the item, take the next
  candidate. Never resolve a rejected push by resetting or force-pushing, which discards
  other sessions' work.
- **Sync against fresh truth:** pull before running `bun run sync`; after any
  `pull --rebase`, re-run sync before pushing, so derived artifacts are regenerated
  against the merged state, never merged textually.
- **`BOARD.md` conflicts are never hand-resolved.** Take either side, re-run sync,
  commit. Same for `ARCHIVE.md` rows.
- **Item-file conflicts are real** (they are the source of truth) but rare by design: one
  assignee per item, other sessions only append log lines. Resolve them by reading, not
  regenerating.

## External trackers

A project may declare an external task tracker in `loops.json` (`trackers.<name>`,
referenced by `projects.<project>.tracker`). A project without one is tracked on this
board alone.

The board owns ticket status: the tracker is a projection of it, never the other way
round. Mapping an item to tickets is encouraged, not enforced; `bun run check` prints a
non-failing advisory for an item at `spec-filed` or later that has decided neither way,
and `tickets: local` settles it. These rules guard someone else's tracker and bind you
whether or not you go through the tool:

- Creating or splitting a ticket is always proposed to the owner, never done on your own
  initiative.
- A ticket a human moved further than the board stays where it is: record a line on the
  item and stop. Reverse a human's change only on the owner's direct prompt.
- Link an item to a ticket on content only by proposal; only mechanical facts link
  without asking.

After a state change in a tracker project, run `bun run tracker-sync status --apply` to
push the projection (forward-only). Agents without tracker access record nothing extra:
the next sync by a host with access catches up. For a commit on an item with tickets,
`bun run tickets <item-slug>` prints the subject suffix and any body line; copy it rather
than composing it.

### Sync ("sync the tracker")

When the owner asks to sync a tracker, when inbox processing pulls a tracker, or before
any `tracker-sync` subcommand other than `status`, read `references/tracker-sync.md`.

## Project registry

`PROJECTS.md` is the indirection layer for per-project locations (repo path, quality gate,
verify gate, specs/follow-up trackers, review-mechanism overrides, notes); `loops.json`
carries the machine-read subset (repo, integration branch, landed adapter, token files,
lifecycle, tracker). Resolve project questions there, keep the two in step, and register a
project before doing unattended work in it.

## Tools

Run from the data-repo root:

- `bun run check` - report-only integrity check; exits non-zero on findings.
- `bun run sync` - regenerate `BOARD.md`, route orphan rows to `OUTBOX.md`, move item
  files per state, append `ARCHIVE.md` rows.
- `bun run check-integration-status [--apply]` - which items' work is on the integration
  branch; `--apply` records `implemented → merged` but performs no Git integration
  (`bun run landed` is an alias).
- `bun run ready` - the dependency gate from board state alone; confirm an `implemented`
  target with `check-integration-status`.
- `bun run tracker-sync status [--tracker <name>] [--apply]` - push board state onto
  linked tickets; plans only without `--apply`. Other subcommands:
  `references/tracker-sync.md`.
- `bun run tickets <item-slug>` - the commit reference for that item's tickets.
- `bun run restamp` - advance `.loops-version` to the DCL clone's HEAD after reviewing an
  upgrade, clearing the drift note `check` prints.
- `bun "$DCL_HOME/tools/cli-registered.ts" --data-repo <data-repo> [--cwd <dir>]` - the
  participation gate, run from a project checkout (Project participation).
